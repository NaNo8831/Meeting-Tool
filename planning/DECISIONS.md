# Durable Decisions

| Date | Decision | Rationale / Notes |
| --- | --- | --- |
| 2026-06-02 | Keep Manual Save visible, available, and required during the structured autosave migration. | PR #72 autosaves only `meeting_settings`; operational runtime state still needs the full-workspace cloud backup in `meetings.meeting_data`. Once structured autosave reliably covers all core meeting data, evaluate retiring Manual Save from the primary workflow or moving it into a secondary backup/export utility role. Do not remove or demote Manual Save in PR #72. |
| 2026-06-02 | Keep Local Workspace supported and browser-only for now; it must not autosave to cloud. Evaluate retirement or developer/testing-only demotion after structured cloud autosave and Phase 3 shared access are stable. | Local Workspace remains a fallback during cloud persistence and shared-access stabilization. Longer term, parallel local and cloud meeting systems create code duplication, testing burden, and user confusion, while the product's team value depends on shared cloud access that Local Workspace cannot provide. Do not remove Local Workspace in Phase 2.5. |
| 2026-06-02 | Hydrate the four `meeting_settings` pilot fields after loading the manual full-workspace backup; keep every non-pilot read on the existing workspace backup path. | The structured settings write pilot must survive refresh without expanding into a broad read-path migration. `meeting_settings.dashboard_title` remains distinct from the cloud container `meetings.name`, and Manual Save to `meetings.meeting_data` remains the full-workspace safety net. |
| 2026-05-31 | Pilot structured autosave with `meeting_settings` only; retain manual `meetings.meeting_data` Save as the full-workspace backup safety net and keep runtime reads on the existing path. | The one-row settings surface is already represented in schema, maps cleanly to dashboard/playbook-level runtime values, avoids broad JSONB autosave regressions, and exercises a member-compatible structured write boundary before Phase 3 access expansion. |
| 2026-05-31 | Keep Defining Objective and Standard Operating Objective cards visually consistent with centered distribution: one to four cards preserve standard width, five cards use the standard width, six cards use the compact maximum row when screen width allows, and seven or more wrap with centered remainder rows. | Leadership teams need to scan objectives quickly during meetings while retaining deeper workflow detail through the Defining Objective detail modal. Future UI work should preserve card scanability and avoid returning full workflow detail to the main meeting view. |
| 2026-05-30 | Keep one meeting notes record per date and lock ended or past meeting notes to read-only review. | The header Start/Edit/View Meeting action resolves to today’s record without duplicates; End Meeting preserves its tactical snapshot behavior while making captured notes read-only. |
| 2026-05-28 | Harden Local Workspace and Cloud Meeting boundaries before autosave. | `/meeting/local` remains browser-only even for signed-in users, Cloud Meeting save/load is limited to valid `/meeting/[id]` cloud routes, and Supabase meeting reads/writes exclude `deleted_at` rows so local state cannot recreate soft-deleted meetings. |
| 2026-05-28 | Surface completed and archived Strategic Topics in a History modal instead of active-list visibility toggles. | Keeps the live Strategic Topics list focused on active discussion while preserving non-destructive archive/completion history and topic-attached Notes. |
| 2026-05-23 | Introduce Phase A/B structured persistence schema as non-breaking Supabase foundation only; keep runtime reads/writes on `meetings.meeting_data` for now. | Adds normalized table and policy groundwork with owner-only RLS while preserving manual Save/Load and JSON export/import until a narrow structured-write pilot is validated. |

| 2026-05-22 | Make `/dashboard` the authenticated Meeting selector with owner-scoped meeting cards and secondary local fallback. | Keeps recurring meeting entry calm and focused, uses existing owner-only RLS for visibility boundaries, and preserves Local Workspace as a non-primary path. |
| 2026-05-22 | Establish routed app foundation: `/` landing, `/dashboard` placeholder, `/meeting/[id]` active workspace route. | Separates authentication entry from operational meeting workspace and creates a stable path for future dashboard evolution without changing existing local/cloud persistence model. |
