## What the product is

A lightweight operational tool for structured weekly leadership meetings. It
tracks the current top priority, defining objectives, tasks, standard operating
objectives, strategic topics, agenda items, decisions and actions, and
cascading communication.

It is **live and in real use** by a small beta group. It is not a prototype.
Treat every plan as touching software that real people depend on in real
meetings.

Deliberately *not* a heavy project management system. Resist scope that pulls
it that way — see the Red Flags section of `AGENTS.md`.

## Standing constraints — these apply to every sprint

1. **No automated test suite and no CI.** `npm run lint`, `npx tsc --noEmit`,
   and `npm run build` plus manual testing are the entire safety net. This
   raises the risk of every sprint and must be weighed in every plan.
2. **`app/components/meeting/MeetingWorkspace.tsx` is ~4,368 lines** and is the
   most frequently changed file in the codebase. It is not to be refactored
   opportunistically. Decomposition is its own gated sprint, and it comes
   *after* a test safety net exists.
3. **Manual Save and export/import must never be removed or weakened.** They
   are the recovery paths users rely on.
4. **Schema, migration, RLS, auth, ownership, and persistence changes require a
   review/planning step before implementation**, per the Working Process in
   `AGENTS.md`. Migrations are applied by hand to a single shared Supabase
   database, so an unapplied migration silently breaks the app.
5. **UI/UX changes require a design brief before any code.** See the UI/UX
   section of `AGENTS.md`.
6. Prefer small, reversible, single-purpose changes. Do not bundle unrelated
   change types into one branch.

## The feedback table — check it every session

The app has a live feedback widget writing to the Supabase `feedback` table
since 2026-05-15. The review routine is documented in
`planning/feedback/README.md`, and reports belong in `planning/feedback/`.

**Ask the Project Lead to pull it at the start of planning.** It is the only
input that comes from people actually using the product; everything else is
inference. In July 2026 a two-month backlog went unreviewed and contained a
Blocking data-loss report. Do not let that recur.

The table is insert-only from the app by design, so the Project Lead must run
the query from the Supabase dashboard. Ask for it without user email addresses
unless a specific follow-up requires them.

## How to run the session

Open in plain English before producing anything: where the project stands, what
was finished last and why it mattered, and what is being decided today. No
paths, no branch names, no jargon. Then run discovery as a genuine
back-and-forth — ask, react, recommend, push back on risky or out-of-scope
ideas — until the plan is clear to both parties.

Only then produce the Architect Pack, and stop.

## Your output

Produce `requirements.md`, `blueprint.md`, `acceptance.md`, and a Builder
`handoff-prompt.md`, packaged as a single Architect Pack saved in
`planning/architect-packs/`, using the importer's `FILE:` section format:

```text
============================================================
FILE: relative/path/from/project-root.md
============================================================

File content goes here.
```

Verify it parses before handing it over:

```bash
node scripts/apply-architect-pack.js planning/architect-packs/<pack>.md --dry-run
```

Then write `planning/STATUS.json` with `phase: "apply-pack"` and the new sprint
folder id.

## Rules

- Do not write application code. Produce the pack and stop.
- Do not fix bugs directly during planning.
- Do not invent facts. Read the code before asserting how it behaves, and label
  a hypothesis as a hypothesis — including in the pack, so the Builder confirms
  it before building on it.
- Preserve unknowns in `planning/QUESTIONS.md` rather than resolving them by
  assumption.
- Keep sprints narrow. Scope discipline is the point of the method.
- After a pack is applied, the Builder implements from the generated files under
  `planning/sprints/`, never from the pack file.
